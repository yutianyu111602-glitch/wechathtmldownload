# Weekly Mini-Program · Atlas Frontend Field Contract

Updated: 2026-06-20 CST

The atlas serving data is being regenerated by a new raw-extraction pipeline.
Until the clean data lands, the mini-program must render the **old** atlas index
without showing fragmented/inflated entities, and must keep working unchanged
when the new (clean) data arrives. This document is the frontend-owned contract
for that.

Implementation: `apps/weekly_activity_miniprogram/utils/atlasContract.js`
Check: `node --test apps/weekly_activity_miniprogram/tests/atlas-contract.test.cjs`

## Endpoints consumed

| Page | Endpoint | Notes |
|------|----------|-------|
| artist | `GET /api/v1/weekly/atlas/artist?name=&eventLimit=&collaboratorLimit=&venueLimit=` | **Honors query limits.** Primary source — request full lists for accurate counts. |
| artist (fallback) | `GET /api/v1/weekly/atlas/dj-profile/{name}` | Hard-caps `venueLimit:15 / collaboratorLimit:20` server-side; counts from it are NOT reliable. Fallback only. |
| venue | `GET /api/v1/weekly/atlas/venue?name=&eventLimit=` | Returns `events`, `residentDJs`. |
| source | `GET /api/v1/atlas/evidence/{ref}` | Session-gated; may 403 / return `publicUrl:{status:"not_public"}`. |

## Field tolerance (old + new)

Helpers accept both camelCase API fields and raw index short keys, so the same
code serves the current index and the rebuilt one:

- venue: `venueName | vn`, `eventCount | ec`, `venueId | vi`
- collaborator/DJ: `displayName | n | name`, `djId | di`, `sameEventCount | eventCount | ec`
- event date: `eventDateStart | event_date_start | date | starts_at | dateLabel`
- event source ref: `sourceRefId | source_ref_id`, `sourceHash | source_hash`

## Entity de-duplication (issue: counts inflated, lists duplicated)

The old index splits one physical venue across several `venue_id`s / name
variants and one DJ identity across several `dj_id`s. The frontend merges
**orthographic** variants and recomputes counts from the merged lists:

- `mergeVenues` / `mergeCollaborators` / `mergeResidentDjs` group by a normalised
  key (lowercase, `&`→`and`, strip `club/俱乐部/bar/酒吧/livehouse/studio/space/空间`,
  strip whitespace + punctuation), sum counts, keep the highest-count variant as
  the display label, sort desc.
- Header counts (`venueCount`, `collaboratorCount`) are overridden with the merged
  list length **when the full list was fetched** (use the high-limit `/atlas/artist`
  route). `eventCount` stays the backend total — per-event dedup needs the full
  event stream and is deferred to the rebuild.

**Out of scope for the frontend (rebuild owns it):** cross-language / semantic
aliases (`OIL` vs `OIL油`, `招待` vs `ZhaoDai`) and address-as-name rows
(`市云岩区…HumClub`). The merges are idempotent — they are no-ops on already-clean
data, so they stay safe after the rebuild.

## Upcoming vs past split (issue: past events in the future list)

`partitionEventsByDate(events)` (venue page):

- **upcoming**: `today <= start <= today + 2 years` → rendered under `未来排期`,
  ascending; this count is the header `未来活动` number.
- **past**: everything else (older than today, undated, or absurd far-future such
  as the old DB's `2046` rows) → rendered under `往期演出`, most-recent first.

The atlas historical merge must never feed the upcoming list directly.

## Source opening / evidence (issue: DJ history "can't open")

- Atlas refs are `src: | source_ref: | activity_src:`-prefixed. A tap must route
  to the **evidence page** (`pages/source/source?kind=atlas`), not the weekly
  source resolver. Keep `sourceRefId` on mapped atlas events — preferring the bare
  `sourceHash` sent taps to `/api/v1/weekly/source/{hash}` which 404s.
- Evidence `publicUrl` is openable **only when it is an http(s) string**. The
  atlas index has no public article URL for historical shows (`not_public` by
  design); render provenance (`sourceTitle / sourceAccount / postDate`, all present
  in the index) plus a muted "no public link" note, and show **no** open button.
- Never fall back to `web-view` for official-account articles (white screen).
