## 1. 你困惑的本质

「每周计划」「每月计划」在数据里通常是两类东西，**不能混成一个 UI 问题**：

| 类型 | 管线里是什么 | 用户要什么 |
|------|--------------|------------|
| **A. 可参加的单场活动** | 独立条 + `agg-child-*`（已从合集拆出） | 像 RA 一样：选一晚、看阵容、去现场 |
| **B. 排期/计划原文** | 父级 aggregate 文（`publish_blocked`）+ 同源推文 | 看俱乐部自己写的「本周安排」「五月月历」 |

若把 B 当成和 A 一样的「城市列表里多几张卡」，会重复、难去重、城市页噪音爆炸。  
**结论：A 进发现流；B 进俱乐部主页的「来源/排期」区，不进城市页正文。**

## 2. 现状（已核实，避免误判）

| 页面 | 实际行为 | 是否等于「俱乐部主页」 |
|------|----------|------------------------|
| `pages/index` | 全国/城市/日期筛选 + 活动列表 + 海报池 | 否，发现首页 |
| `pages/city` | 城市目录 → 点城市 **回到 index 带 city 参数** | 否，只是入口 |
| `pages/venue` | 按名称模糊匹配 `venue/promoter/account`，展示 `UPCOMING EVENTS` + `SOURCE ARTICLES` | **近似，但还不是正式俱乐部主页** |
| `pages/detail` | 单场活动；可跳 `venue` | — |

管线侧（`expand_weekly_aggregate_articles.py`）已识别：`排期|计划|月历|月度安排|weekly agenda|monthly schedule` 等 → aggregate 车道；父文不进 feed，子场进 feed。

前端 `sourceArticles.js`：场馆页把同源 hash 聚成「排期原文 / 原文」，**已放在 venue 页，不在 city 页**。

**所以你感觉「俱乐部主页好像也没有」——对一半：**  
有 `venue` 页，但缺 **稳定俱乐部 ID、档案、排期区与月/周分层**，名字匹配也不等于 RA 式 Venue Profile。

## 3. 决策（由我拍板，可直接按此做产品）

### 3.1 主归属：**俱乐部主页（Venue / Organizer Profile）**

周排期、月排期 **默认只挂在俱乐部主页**，不放在城市页主体。

理由（RA 参照 + 你们去重模型）：

1. **作者域**：排期文来自俱乐部公众号，语义归属 `venue_scope + account`，不是「上海市」。
2. **去重域**：`date + city + venue_scope` 的合并与冲突都在馆级；城市页堆多馆排期文会引入跨馆误读。
3. **用户心智**：用户想查「OIL 本周怎么排」会找馆；想查「深圳周末去哪玩」用城市筛选首页即可。
4. **已有实现方向**：`SOURCE ARTICLES` 已在 `venue`；只需 **升格为「俱乐部主页」并细分排期类型**，而不是搬到 `city`。

### 3.2 城市页角色：**发现透镜，不承载排期正文**

`city` 保持：**选城市 → index 筛选**。可选增强（P2，非必须）：

- 城市筛选结果顶栏：**「本周 N 场 · M 个场馆有排期文」**（统计，不是全文）
- 列表卡片副标题已有场馆名 → 点进 **俱乐部主页**

**禁止**：在城市页嵌入「本月活动安排」全文或多馆排期瀑布流。

### 3.3 首页角色：**全国发现；排期文不单独占卡**

首页列表只展示 **类型 A（单场/子场）**。  
类型 B 不单独占一行活动卡（父 aggregate 已 `publish_blocked`，与设计一致）。

用户路径：首页看到某馆今晚的场 → 详情 → 俱乐部主页 → 看本周/本月排期原文。

## 4. 目标信息架构（俱乐部主页应长什么样）

将现有 `pages/venue` **升级为** `Club Profile`（名称可仍叫 venue，逻辑升级）：

```
┌─────────────────────────────────────┐
│ 俱乐部名 · 城市 · 地址（可复制）      │
│ 运营状态（active/inactive，registry）│
├─────────────────────────────────────┤
│ UPCOMING EVENTS                     │  ← 类型 A，按日期排序
│  （含 agg-child，已去重后的单场）     │
├─────────────────────────────────────┤
│ SCHEDULE & SOURCES                  │  ← 类型 B，按馆聚合
│  · 本周排期 / weekly agenda  [标签]  │
│  · 本月安排 / monthly schedule [标签]│
│  · 其他活动原文                      │
├─────────────────────────────────────┤
│ ABOUT（bio，来自 registry/首条）    │
└─────────────────────────────────────┘
```

### 4.1 周 vs 月：同一区块，不同标签（不拆两个顶级页）

| 维度 | 建议 |
|------|------|
| 是否两个 Tab「周/月」 | **否**（初期）；一个列表 + `horizon` 徽章即可 |
| 排序 | 排期文按 `source_published_at` 降序；下面仍是 UPCOMING 按 `event_date_start` |
| 点击 | 进 `pages/source` 或原文链接，**不**再生成假活动卡 |

管线需下行（未来，非本计划写代码）：`schedule_horizon: week | month | unknown`（由 aggregate 标题规则打标）。

### 4.2 与去重计划的关系

- 列表里的场 = L2 发布包已合并后的 **事件卡**（见 `PLAN_DEDUP_LOGIC_RA_20260520.md`）。
- 排期原文 = **溯源层**，不参与列表 dedupe；同一 hash 在俱乐部主页只出现一次。
- 城市页 **不参与** 排期 hash 聚合。

## 6. 边界案例（计划内写清，避免以后又纠结）

### 6.1 一文多场、跨馆合集（如部分 WTR）

- **子场**：仍按馆出现在各自俱乐部主页 UPCOMING。
- **父文**：挂在 **发文账号主页**；若账号=合集号而非单馆，用 `organizer_id=account` 的 **主办方页**，不要硬塞进每个城市页。
- 城市页最多显示：「该城市本周有 X 场来自合集 Y」**链接**，不嵌全文。

### 6.2 馆名不一致（`venue` 页当前痛点）

计划要求俱乐部主页主键改为 **`venue_registry_id` 或 `organizer_key`**，展示名可别名；  
**禁止**长期用 `includes` 模糊匹配当主页（现状技术债，写入 P1 改造项）。

### 6.3 月排期覆盖窗口 > 发布窗口（15 天）

- 列表仍只展示 **发布窗口内** 的子场（现有 gate）。
- 月排期原文可展示 **全文**，但标注「部分日期超出当前查询窗口，以原文为准」。

## 8. 一句话答案（给你备忘）

- **每周/每月计划（排期推文）→ 俱乐部主页的「排期与来源」区，不要放城市页。**
- **城市页 → 只负责「在这个城市发现有哪些场」；点场馆进俱乐部主页看排期原文。**
- **你现在没有的是「正式俱乐部主页」，不是完全没有页面——`venue` 要升级，而不是把排期搬到 `city`。**
